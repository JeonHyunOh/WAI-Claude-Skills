# intent-init

아이디어 한 줄 → 의도 인터뷰 → INTENT.md + CLAUDE.md 생성 → 실행 준비 완료.

## Inputs

- `$1` (선택) — 한 줄 아이디어. 없으면 Phase 1에서 수집.

---

## Phase 0 — 사전 점검

파일 생성 전에 현재 디렉토리 상태 확인:

```bash
ls -A
```

분기:
- 비어있음 → 현재 위치에서 진행
- `INTENT.md` 또는 `CLAUDE.md` 이미 존재 → 사용자에게 알림: "이미 세팅된 프로젝트입니다. `/intent-apply`를 사용하세요." → 중단
- 비어있지 않음 → AskUserQuestion: "(a) 현재 폴더에서 계속 (b) 중단"

---

## Phase 1 — 의도 인터뷰

"의도 인터뷰를 시작합니다 (5~10분)" 안내 후 다음을 사용자에게 설명:

> "지금부터 **왜 만드는지(Why)**를 먼저 정리합니다.
> '무엇을 만들지'보다 '왜 필요한지'가 먼저입니다.
> How(어떻게)는 절대 쓰지 않습니다 — AI가 결정합니다.
> 불확실한 것은 (?)로 표시하고 넘어갑니다."

### 인터뷰 질문 순서

각 질문에 답변 수집 후 다음 질문으로 진행. 답이 모호하면 1회만 명확화 질문.

| # | 섹션 | 질문 |
|---|------|------|
| 1 | **Why** | 지금 무엇이 불편한가? 왜 이걸 만들어야 하는가? |
| 2 | **Why** | 누가 이 고통을 겪는가? 이 프로젝트가 없으면 어떤 일이 생기는가? |
| 3 | **What** | 이걸 쓴 사람이 할 수 있게 되는 것은? (기능이 아닌 **결과**로) |
| 4 | **What** | 첫 버전에서 반드시 달성해야 할 결과 3~5개는? |
| 5 | **What** | 성공을 어떻게 검증할 것인가? (테스트·지표·시나리오) |
| 6 | **Not** | 이번 버전에서 절대 하지 않을 것 3개 이상은? |
| 7 | **Not** | 가장 두려운 실패 시나리오는? 이를 막는 경계선은? |
| 8 | **Not** | AI에게 절대 맡기지 않을 결정은? (보안·비용·데이터 등) |

**How 리다이렉트 규칙**: 사용자가 구현 방식을 말하면 즉시:
> "'어떻게'가 아닌 '무엇이 되어야 하는지'로 말씀해주세요.
> 예: 'Redis 사용' → '캐시 레이어 금지' 또는 '응답이 즉각적이어야 한다(200ms 이하)'"

---

## Phase 2 — INTENT.md 작성

인터뷰 답변을 정리해 `INTENT.md` 작성. **How가 들어가지 않도록** 검토.

```markdown
# INTENT — [프로젝트명]

> lifecycle: exploring

## Why

[누가, 어떤 고통을, 왜 지금 — 인터뷰 1·2번 답변 통합]

## What

결과 (기능이 아닌 사용자가 할 수 있게 되는 것):
- [ ] [결과 1]
- [ ] [결과 2]
- [ ] (?) [불확실한 항목]

성공 기준:
- [검증 방법 1]
- [검증 방법 2]

## Not

절대 하지 않을 것:
- [제약 1]
- [제약 2]
- [제약 3]

AI에게 맡기지 않을 결정:
- [결정 1]

실패 방지 경계선:
- [경계선]

## Learnings

<!-- 세션마다 배운 것을 여기에 누적한다. 날짜와 함께 기록. -->
```

작성 후 사용자에게 보여주고 AskUserQuestion: "(a) 이대로 진행 (b) 수정 (c) 처음부터)"

## Phase 3 — CLAUDE.md 생성

INTENT.md 기반으로 프로젝트 전용 `CLAUDE.md` 생성.

```markdown
# CLAUDE.md

이 프로젝트는 **의도공학 + Karpathy 가이드라인**을 결합한 프레임워크로 운영됩니다.

## 의도 문서

모든 작업은 `INTENT.md`의 Why/What/Not에 기반합니다.
- 요청이 Why/What에 매핑되지 않으면 먼저 물어볼 것
- Not 섹션의 제약은 절대 위반하지 말 것
- 새로운 발견은 Learnings에 기록할 것

---

## 실행 원칙 (Karpathy)

### 1. 코딩 전에 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

- 가정을 명시적으로 밝힐 것. 불확실하면 물어볼 것.
- 여러 해석이 가능하면 모두 제시할 것 — 조용히 하나만 고르지 말 것.
- 더 단순한 접근법이 있으면 말할 것.
- 불명확한 것이 있으면 멈추고 물어볼 것.

### 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드는 없음.**

- 요청받은 것 이상의 기능 추가 금지.
- 단일 사용 코드에 추상화 금지.
- 요청하지 않은 유연성·설정 가능성 금지.
- 200줄로 썼는데 50줄로 될 수 있다면 다시 쓸 것.

스스로에게 물어볼 것: "시니어 엔지니어가 보면 과하다고 할까?" 그렇다면 단순하게 만들 것.

### 3. 외과적 수정

**반드시 필요한 것만 건드릴 것. 내가 만든 것만 정리할 것.**

- 인접한 코드·주석·포맷 개선 금지.
- 망가지지 않은 것 리팩토링 금지.
- 기존 스타일 맞출 것 (내 방식과 달라도).
- 관련 없는 데드 코드 발견 시 언급만 할 것 — 삭제 금지.

판단 기준: 변경된 모든 줄이 사용자의 요청으로 직접 이어져야 한다.

### 4. 목표 기반 실행

**성공 기준을 정의할 것. 검증될 때까지 루프를 돌 것.**

작업을 검증 가능한 목표로 변환:
- "기능 추가" → "이 시나리오가 통과하면 성공"
- "버그 수정" → "이 테스트가 통과하면 성공"
- "리팩토링" → "전후로 테스트 통과"

여러 단계 작업은 계획을 먼저 제시:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
```

## 태스크 실행 템플릿

매 작업 시작 전 이 형식으로 의도를 확인:

```
What: [무엇이 되면 성공인가]
Not: [이번 작업에서 건드리지 않을 것]
성공 기준: [어떻게 검증할 것인가]
```

---

## 이 지침이 작동하고 있다면

- diff에 불필요한 변경이 없다
- 요청 전에 가정을 드러내고 물어본다
- 코드가 요청받은 것만큼만 복잡하다
- INTENT.md의 Not을 위반하지 않는다
```

```
  3. What 항목이 완료되면 [ ]를 [x]로 체크
```

## Guardrails

- **How 리다이렉트 강제**: 인터뷰 중 구현 방식이 나오면 즉시 리다이렉트
- **Not의 절대성**: CLAUDE.md 생성 시 INTENT.md의 Not을 그대로 이식
- **불확실성 인정**: (?) 표시 사용 — 지금 모르는 건 모른다고 기록
- **최소 Not 3개**: Not 섹션에 최소 3개 미만이면 더 물어볼 것

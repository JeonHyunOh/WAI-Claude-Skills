# intent-apply

기존 프로젝트 분석 → 의도 인터뷰 → INTENT.md + CLAUDE.md 생성/업데이트.

---

## Phase 0 — 코드베이스 스냅샷

먼저 현재 프로젝트 상태를 파악한다. 병렬로 실행:

```bash
# 프로젝트 구조
find . -maxdepth 3 -not -path '*/node_modules/*' -not -path '*/.git/*' -not -path '*/__pycache__/*' | sort

# 기존 문서 확인
ls -la *.md 2>/dev/null; ls -la docs/ 2>/dev/null

# 패키지/의존성 (있다면)
cat package.json 2>/dev/null | head -20 || cat pyproject.toml 2>/dev/null | head -20 || cat go.mod 2>/dev/null | head -10

# 최근 커밋 히스토리
git log --oneline -15 2>/dev/null
```

분석 결과를 바탕으로 사용자에게 현재 상태 요약:
> "이 프로젝트는 [언어/프레임워크], [주요 디렉토리 구조], [최근 활동]으로 파악됩니다."

**기존 파일 처리**:
- `INTENT.md` 이미 존재 → 내용 읽고 Learnings 추가 모드로 진입 (덮어쓰지 않음)
- `CLAUDE.md` 이미 존재 → 기존 내용 보존 + 프레임워크 섹션 병합 제안

---

## Phase 1 — 의도 역산 인터뷰

코드베이스 분석 내용을 바탕으로 인터뷰. 파악된 내용은 가설로 제시하고 확인:

> "코드를 보니 [파악한 내용]인 것 같습니다. 맞나요?
> 지금부터 **왜 만들었는지(Why)**를 정리합니다.
> How(어떻게)는 이미 코드에 있으니, 우리는 Why/What/Not에 집중합니다."

### 인터뷰 질문

| # | 섹션 | 질문 |
|---|------|------|
| 1 | **Why** | 이 프로젝트를 처음 시작한 이유는? 어떤 문제를 풀려고 했나? |
| 2 | **Why** | 이게 없으면 누가 가장 불편한가? 지금도 그 문제가 맞나? |
| 3 | **What** | 현재 이 프로젝트가 실제로 해결하고 있는 것은? (코드 기준이 아닌 사용자 결과 기준) |
| 4 | **What** | 앞으로 3개월 안에 달성하려는 결과는? |
| 5 | **What** | 지금 가장 중요한 미완성 부분은? 완료를 어떻게 판단할 것인가? |
| 6 | **Not** | 이 프로젝트에서 절대 하지 않기로 결정한 것은? (의도적 제약) |
| 7 | **Not** | 과거에 시도했다가 포기한 것이 있다면? 이유는? |
| 8 | **Not** | AI가 임의로 결정하면 안 되는 영역은? (보안·비용·아키텍처 등) |

**가설 제시 방식**: 코드에서 파악된 내용을 가설로 먼저 말하고 확인/수정 받기.
예: "코드를 보니 Redis를 캐시로 쓰고 있는데, 이게 Not에 들어가야 하는 결정인가요, 아니면 바꿀 수 있는 구현 선택인가요?"

## Phase 2 — INTENT.md 생성/업데이트

### 신규 생성

```markdown
# INTENT — [프로젝트명]

> lifecycle: [exploring / clarified / build — 현재 상태에 맞게]
> last updated: [날짜]

## Why

[누가, 어떤 고통을, 왜 지금 — 인터뷰 1·2번 답변 통합]

## What

현재 달성하고 있는 것:
- [x] [이미 된 것]
- [x] [이미 된 것]

앞으로 달성할 것:
- [ ] [결과 1]
- [ ] [결과 2]
- [ ] (?) [불확실한 항목]

성공 기준:
- [검증 방법]

## Not

의도적 제약 (절대 하지 않을 것):
- [제약 1]
- [제약 2]

시도했다가 포기한 것:
- [항목] — 이유: [이유]

AI에게 맡기지 않을 결정:
- [결정 영역]

## Learnings

[날짜] — 프레임워크 적용: 기존 프로젝트에 의도공학 + Karpathy 가이드라인 세팅.
[코드베이스 분석에서 발견한 주요 패턴이나 결정들 기록]
```

### 기존 INTENT.md가 있는 경우

기존 내용을 보존하고 Learnings에 추가:
```markdown
## Learnings

[기존 내용 유지]

[날짜] — intent-apply 실행: [새로 발견한 내용 또는 업데이트된 내용]
```

작성 후 사용자에게 보여주고 AskUserQuestion: "(a) 이대로 저장 (b) 수정 (c) 취소"

## Phase 3 — CLAUDE.md 생성/병합

### 기존 CLAUDE.md 없는 경우 → 생성

```markdown
# CLAUDE.md

이 프로젝트는 **의도공학 + Karpathy 가이드라인**을 결합한 프레임워크로 운영됩니다.

## 의도 문서

모든 작업은 `INTENT.md`의 Why/What/Not에 기반합니다.
- 요청이 Why/What에 매핑되지 않으면 먼저 물어볼 것
- Not 섹션의 제약은 절대 위반하지 말 것
- 새로운 발견은 Learnings에 기록할 것

---

## 실행 원칙 (Karpathy)

### 1. 코딩 전에 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

- 가정을 명시적으로 밝힐 것. 불확실하면 물어볼 것.
- 여러 해석이 가능하면 모두 제시할 것 — 조용히 하나만 고르지 말 것.
- 더 단순한 접근법이 있으면 말할 것.
- 불명확한 것이 있으면 멈추고 물어볼 것.

### 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드는 없음.**

- 요청받은 것 이상의 기능 추가 금지.
- 단일 사용 코드에 추상화 금지.
- 요청하지 않은 유연성·설정 가능성 금지.
- 200줄로 썼는데 50줄로 될 수 있다면 다시 쓸 것.

스스로에게: "시니어 엔지니어가 보면 과하다고 할까?" 그렇다면 단순하게.

### 3. 외과적 수정

**반드시 필요한 것만 건드릴 것. 내가 만든 것만 정리할 것.**

- 인접한 코드·주석·포맷 개선 금지.
- 망가지지 않은 것 리팩토링 금지.
- 기존 스타일 맞출 것 (내 방식과 달라도).
- 관련 없는 데드 코드 발견 시 언급만 할 것 — 삭제 금지.

판단 기준: 변경된 모든 줄이 사용자의 요청으로 직접 이어져야 한다.

### 4. 목표 기반 실행

**성공 기준을 정의할 것. 검증될 때까지 루프를 돌 것.**

작업을 검증 가능한 목표로 변환:
- "기능 추가" → "이 시나리오가 통과하면 성공"
- "버그 수정" → "이 테스트가 통과하면 성공"
- "리팩토링" → "전후로 테스트 통과"

여러 단계 작업은 계획을 먼저 제시:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
```

## 태스크 실행 템플릿

매 작업 시작 전 이 형식으로 의도를 확인:

```
What: [무엇이 되면 성공인가]
Not: [이번 작업에서 건드리지 않을 것]
성공 기준: [어떻게 검증할 것인가]
```

---

## 이 지침이 작동하고 있다면

- diff에 불필요한 변경이 없다
- 요청 전에 가정을 드러내고 물어본다
- 코드가 요청받은 것만큼만 복잡하다
- INTENT.md의 Not을 위반하지 않는다
```

### 기존 CLAUDE.md가 있는 경우

기존 내용 읽은 후 AskUserQuestion:
"(a) 기존 CLAUDE.md 맨 위에 의도공학 섹션 추가
 (b) 기존 내용 뒤에 추가
 (c) 새 파일로 CLAUDE.intent.md 생성
 (d) 건너뜀"

선택에 따라 병합. 기존 내용은 절대 삭제하지 않음.

## Phase 4 — 태스크 템플릿 제공

매일 작업할 때 쓸 수 있는 템플릿을 출력:

```
## 오늘의 작업 의도

What: [무엇이 되면 성공인가 — INTENT.md의 What 항목 참조]
Not:
  - [이번 작업에서 건드리지 않을 것]
  - [INTENT.md의 Not에서 관련 항목]
성공 기준: [테스트·시나리오·지표 — 구체적으로]

---
[작업 시작]
```

이 템플릿을 매 작업 시작 전에 채우면 의도공학 + Karpathy가 자동으로 작동한다.

## Guardrails

- **기존 파일 보존 우선**: INTENT.md·CLAUDE.md가 있으면 덮어쓰지 말고 병합
- **가설 제시 방식**: 코드에서 추론한 내용은 단정하지 말고 가설로 제시 후 확인
- **How를 Not으로 변환**: "Redis 쓰고 있다"는 사실을 "Redis 교체 금지" 또는 "캐시 전략 변경은 논의 필요"로 Not에 명시화
- **Learnings 날짜 기록**: 모든 Learnings 항목에 날짜 포함
- **최소 Not 3개**: Not 항목이 3개 미만이면 더 파악하거나 물어볼 것
- **병렬 분석**: Phase 0의 bash 명령은 병렬 실행
